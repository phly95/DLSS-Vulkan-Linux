# MiMo assessment: what the last 53 commits actually did, and what DLSSNR-AMD's method would change

Written 2026-10-25 23:01 EDT by MiMo-V2.6-Flash (OpenCode) for the session that picks this up next.
This is a *decision record* in the same shape as `DEEPSEEK-ASSESSMENT.md`: a question, a verdict, the
evidence, and what to do first. It does not restate `HANDOFF.md`, which stays authoritative for project
state and for the do-not-retry rules. Read this first, then `HANDOFF.md`, then `tools/verify/README.md`.

Everything below is either (a) **measured** in this repository — the commit, file or command is named —

## 1. The question that was asked

> Look through the commits since `3cc147e` for progress, regressions and exposed gaps; then compare the
> porting method with `mochizuki0323/DLSSNR-AMD` and say whether its method would make the Vulkan port
> happen faster, or whether it is already the same method.

Two parts: **what happened here**, and **what could be borrowed**.

## 2. Verdict

**Part 1 — the last 53 commits are real breadth plus a real walk-back.**
From a `HANDOFF.md` that said *"Vulkan shaders: not started"* to every SR and RR kernel existing,
five new launch-exact kernels, and a referee harness that passes V1/V2/V5/V6/V7/V10. Against that,
headline pipeline quality was reported at 108.02 dB, then 54.16, then 42.40, then **27.79/30.06 dB**, and
frame time at 0.40 ms, then **57.772 ms** — the later record calls the earlier ones "superseded" and
`docs/OPEN.md` still marks the gap **unexplained**. Kernel-level diffdump numbers, unlike the pipeline
numbers, moved monotonically and nothing that is EXACT today was later lost.

**Part 2 — the two projects use different methods, and one of them is already vendored here.**
`reference-nr-vulkan/` **is** `mochizuki0323/DLSSNR-AMD`: `.gitmodules` points at that URL, pinned
`c71b0f4` (their 2026-10-20 commit). Our NR figures (45.59 / 47.97 / 49.00 dB) are theirs
(45.56 / 47.99 / 49.06 dB) because it is the same code. The comparison is therefore not "us vs a stranger";
it is *their NR method* vs *our SR/RR method*, side by side in one tree — and **the largest efficiency
gain available (the NGX/Proton host bridge that our V9 path is missing) is MIT code sitting inside this
repository already.**

**Estimate:** adopting items §7.1–§7.4 would remove most of the non-research work still blocking
deliverables 6 and 7, without changing the referee's contract.

**a. Quality claims collapsed, in four steps.**

| commit | time | claim |
| --- | --- | --- |
| `707155f` | 13:13 | SR M **mean 108.02 dB**, min 77.36, "passes V4"; SR L 91.81; RR F 45.88 |
| `707155f` | same commit | V4 `sr_M_seq` **37.55 dB** — cannot both be right |
| `4ec6263` | 14:25 | `sr_M_seq` mean **54.16 dB**, 6 frames >60 dB |
| `c2e1f37` | 15:17 | `sr_M_seq` mean **42.40 dB**, min 40.87 ("+8.4 dB") |
| `3cd0c8d` | 19:26 | SR M **27.79/30.06**, SR L 26.08/29.45, RR F 26.76/27.15 — earlier claims "superseded" |

**b. Timing claims collapsed ~145×:** 0.39–0.40 ms/frame SR at 256x144 (`707155f`) → **57.772 / 58.145 ms**
median at the same resolution (`3cd0c8d`). RR moved only 0.67 → 0.76 ms, so the discrepancy is
SR-specific — consistent with a change in *what was inside the timestamps*, not only slower code.

**c. `ngx_client / Proton` was downgraded EXACT → APPROX.** At `c2e1f37` the row read *"All 16 NGX
exports implemented; passes D3D12 and Vulkan validation… 12/12 frames read back."* Measured now: both
`NVSDK_NGX_D3D12_EvaluateFeature` and `NVSDK_NGX_VULKAN_EvaluateFeature` in `src/pe/nvngx.cpp` fetch the
`Output`/`Color` resources, touch nothing and return success — and have done since the first breadth
commit `6135cee`. The later trace showed 12 output files of zeros. `ec476d4` names it correctly:
*missing NGX resource bridge*.

**d. A status claim was withdrawn and re-earned.** `k_ae_block`/`k_ae_final` were listed EXACT in the
morning; `d839407` withdrew it (*"the current shader does not match NeuralHub's launch ABI"* — port
144 f32 elements vs oracle 2 u32). It was re-earned at `d7906f5` after a real ABI/ISA decode;
`k_ae_final` remains APPROX with `E0c22[3]` wrong (implied step factor ≈ 0.2413, no clean fraction).

**e. Units changed under the numbers.** `0ccb5f6` and `7c4d96f` corrected RR output dtypes, `d84952c`
corrected pooled2's channel encoding (10:10:10:2, *not* R11G11B10), and `sr_post full15` is reported as
32.49% in u8 units and 10.21% in u32 units for the same kernel. Some of the day's jumps and drops are
reinterpretation, not code change.

## 5. Gaps the sequence exposed

1. **No reproducible pipeline metric.** `grep -rn "Mean PSNR\|Min PSNR" --include=*.py --include=*.cpp
   --include=*.sh` over the tree returns **nothing**; `src/` computes no PSNR at all. Every whole-pipeline
   number came from tooling outside the repository. That is the direct cause of 108 → 54 → 42 → 30 dB drift.
2. **Integration is a shell.** The installer passes; `EvaluateFeature` never dispatches. Nothing in-game
   works regardless of kernel quality, and `run_all.sh`'s output-comparison stage (line 376–381) is never
   reached because V4 or V9 fails first — so V9's "PASS (all 14 tests)" only ever meant create/cycles/refusal.
3. **V4 is ~20 dB away.** Best honest replay ≈ 30 dB mean against a ≥50/55 dB requirement.
4. **Attempt budgets are being consumed where the leverage is low.** `k_sr_downsample` attempts 1–5 (four
   of them arithmetic-order work) moved a kernel whose chain PSNR was already 75.37 dB, while
   `k_sr_stage`, `k_level` (0.29%) and `k_sr_enc0` `t0` (0.92%) — where the network's error lives — sit at
   0.3–1.3% bit-exact.
5. **Smoke-only kernels:** `k_rr_avg2x2`, `k_rr_ds_*`, `k_sr_ae_*`, `k_sr_gather_mv`,
   `k_sr_unorm8_table` have "O7 passed" and no oracle-launch fidelity.
6. **`rr_level` max \|err\| moved 1.25 → inf** between `4ec6263` and today (bit-exact still ~0.29%) — either
   a different measured launch or a real backslide. **Estimate:** worth one command to disambiguate before
   it is cited either way.

## 6. How DLSSNR-AMD's method differs (measured: their `docs/ARCHITECTURE.md`, `CLAUDE.md`, and the vendored tree)

| | **DLSSNR-AMD (vendored as `reference-nr-vulkan/`)** | **This repo's SR/RR port** |
| --- | --- | --- |
| Source of truth | the **model descriptor**: layer names/types in the extracted model (`CCVit1DAttention`, `CCDecInputUpsample`…) mapped by a 7,320-line `nr_graph.cpp` to generic kernels | the **HIP ISA**: NeuralHub's hand-written kernels disassembled and decoded instruction by instruction |
| Unit of porting | 9 shader bodies, ~7.7k lines GLSL, one `pipelines.json` listing every pipeline and its defines → ~150 layers | one `.comp` per kernel family with hand-decoded push-constant offsets in `runner.cpp` |
| Verification | **end-to-end only**: their build vs NVIDIA's real `nvngx_dlssnr.dll` on an RTX 5090 through NGX; PSNR/SSIM tables in `docs/ngx-verification/*`; explicitly *"not bit-identical"* | **per launch, bit level**: `diffdump.py` vs srref/rrref (NeuralHub's own kernels on this card); EXACT/CLOSE/APPROX; V4/V9 is the referee gate |
| Precision rule | written down once: *FP8 where the original uses FP8, FP16/FP32 elsewhere; changing reduction order changes the picture* | emergent per attempt: Dekker residuals, fp16 FMA chain order, balanced softmax trees |
| host↔shader contract | `shader-constants.txt`; *the runtime refuses a shader folder that disagrees* | manual `memcpy(push + 248, …)`; mismatches found by diffing dumps |
| integration | 16,267 lines in `linux/src/pe/`, incl. a working `EvaluateFeature` (`nr_ngx_core.cpp:720`), `nr_pe_session.cpp` (3,678 lines) recording into the game's own command list, `nr_pe_interop.cpp` for vkd3d-proton formats | 384 lines in `src/pe/nvngx.cpp`, both `EvaluateFeature` exports are no-op success stubs |

**Where their method does not transfer:**

- **They have no oracle; we do.** srref/rrref run NeuralHub's own kernels, so a mismatch is attributable
  to one kernel and one launch. For NR they can only see the end-to-end number. Diffdump is the better
  *diagnostic*; their method is a better *gate*. Keep both.
- **SR/RR ≠ NR structurally.** NR is a layer table — descriptors in the model. SR/RR are hand-written
  temporal kernels with packed formats, history parity and host ABIs; no descriptor exists to be generic
  against. Our dominant error class has been **ABI/layout**, not arithmetic.
- **Their acceptance bar would fail our referee.** "Close but not bit-identical, 45.5 dB vs the vendor"
  is a product claim; our rules define EXACT/CLOSE with pasted numbers, and the goal is numerical parity
  with the Windows build. Adopting their bar changes the deliverable, not the process.
- **They never shipped SR or RR.** 197 stars and a working installer notwithstanding, the temporal half
  of this project is unsolved in their code.

## 7. Efficiency gains, ranked

1. **Port the `pe` bridge; do not invent one.** Adapt `reference-nr-vulkan/linux/src/pe/nr_ngx_core.cpp`
   + `nr_pe_session.cpp` (D3D12 record-into-list, D3D11 own-buffer, Vulkan) + `nr_pe_interop.cpp`
   (vkd3d-proton format families) to SR/RR parameters — our `tools/verify/ngx_client` already carries the
   SR/RR NGX names. Replaces the no-op `EvaluateFeature`, unblocks deliverable 6 and V9's output stage.
   MIT, already in the tree. **Estimate: the largest single block of remaining non-research work.**
2. **Commit one end-to-end harness in their style.** Fixed inputs, one command, a tabulated
   PSNR/SSIM/timing table checked into `docs/`. This is what would have made 108/54/42/30 dB impossible
   to write, and it makes every future claim reviewable from a clean clone.
3. **Budget kernels by chain leverage.** Measure each kernel's contribution to end-to-end dB with oracle
   inputs (the machinery exists: `diffdump.py` "chain with oracle inputs" rows), stop ULP work on
   anything already ≥60 dB chain PSNR, and move the attempts to `enc0` / `stage` / `level`.
4. **Add a host↔shader manifest** in their `pipelines.json` + `shader-constants.txt` pattern, so push
   layouts and dtypes are declared once and checked at load. This kills the bug class that ate the
   evening session: the `rr_post` packed plane, `push+8` holding `W` instead of `W0` (`3cd0c8d`), the
   missing `jitter_prev` (`c2e1f37`), the dtype misreads (`0ccb5f6`, `7c4d96f`).
5. **Bake the dispatch plan** for the 18-instantiation families (`nr_native_plan_data.hpp` is their
   pattern) instead of hand-wiring each dispatch in `runner.cpp`.
6. **Keep diffdump as diagnosis, not as the definition of done** — EXACT where it falls out cheaply
   (gather, post_prep, pooled2, AE did), CLOSE/APPROX with a stated chain-PSNR contribution elsewhere.
   That is already legal under the referee's rules.

**Do not copy:** Windows ACO Mode, RenoDX style, int4 mixed, the menus and routes — all NR-product scope
with no bearing on the SR/RR gate — and do not adopt "not bit-identical" as an acceptance criterion.

## 8. What a later session should do first

1. Read `HANDOFF.md` (authoritative state, audit, do-not-retry) and `tools/verify/README.md`.
2. Reconcile the measurement before citing any pipeline number again: commit one script that prints the
   PSNR/timing table (§7.2), re-run it on the restored oracle sequence, and either explain or delete the
   108 dB and 0.40 ms claims still visible in history.
3. Then take §7.1 — the `pe` bridge — because it is the only item that unblocks a whole deliverable
   rather than improving a number.
4. Spend kernel attempts only where the chain leverage says so (§7.3); do not spend another attempt on
   `k_sr_downsample` or `k_rr_downsample` ordering.
5. Confirm `rr_level`'s max-error change (§5.6) before it is used as evidence in either direction.
